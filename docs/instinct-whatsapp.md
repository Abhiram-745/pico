# Instinct and WhatsApp: read-only first slice

Repository research found no definition of **Instinct** in settings, watch targets, app lists, bridge code or existing docs. This does not claim an Instinct product integration. Clarifying its identity and intended data contract remains necessary.

## Working locally

WhatsApp is an opt-in Workspace target, available in Workspace management, desktop watch Settings and island watching preferences. Enable watching and select WhatsApp. On Windows, existing read-only window discovery observes WhatsApp Desktop or a visible WhatsApp Web browser window title. Titles such as `(3) WhatsApp` indicate an observed unread badge. The island shows the count and its source, and Workspace retains an actionable review card with explicit Open/Dismiss controls. Repeated counts dedupe; changed counts create a new observation. Clearing the badge clears the current card. Removing the target removes retained observations. No credentials are needed for this path.

This is a title observation, **not message content, new-message detection, or inbox access**. A plain open WhatsApp window proves nothing about unread messages. Same-count replacement cannot be detected from a badge. Hidden browser tabs, tray-only windows, browser title behavior and localized/different badge formats may expose nothing. Windows must expose the title to the bridge's existing window enumerator. Open only focuses an unambiguous current window after a user gesture. No private WhatsApp databases, browser sessions, cookies, accessibility message content, hidden APIs or automatic sends are used by this adapter. Windows runtime behavior still needs a Windows bridge smoke test; offline fixtures validate interpretation only.

## Connected email and updates

Existing Composio watch remains opt-in and requires a Composio API key, enabled Tools, an authorized Gmail/Outlook/Calendar account, explicit account selection and the corresponding watch toggle. Live key is pending. Gmail and Outlook unread samples now distinguish message identity/content, even with an unchanged unread count, without claiming that sampled unread mail is newly delivered mail. Subjects are bounded and credential-filtered before display. Calendar remains a bounded upcoming-event sample. Provider faults are isolated; removed sources invalidate summaries and retained cards. Collection uses independent adaptive local and remote clocks, with bounded source/provider waits (exact timing below). No OAuth configuration was changed.

Outlook's `OUTLOOK_QUERY_EMAILS` adapter uses the official OData `filter`, inbox folder, bounded metadata selection and advertised field/type validation. Exact SDK arguments and incompatible-schema rejection are offline tested. Live tenant access still requires credentials. A provider schema mismatch surfaces as unavailable, not invented mail. Samples are bounded, not complete inbox counts. Observations and dismissal memory are in-process only. Quiet mode suppresses event flashes, while the island still displays current watch details; active foreground agent/voice/approval states retain priority.

## Future authenticated path

First define Instinct's integration contract. Message-content access would require a separately designed authenticated WhatsApp Business Platform/Cloud API integration (business account, registered phone number, app/access token, required permissions and verified webhook setup), or an explicitly supported Composio WhatsApp toolkit with its credentials and authorized account. Neither path is implemented or connected here. Business API availability does not imply access to a personal WhatsApp Desktop inbox. Any outbound action needs explicit product design and user authorization; this slice only observes titles.

Offline regression: `npm run check:workspace`. Also run `npm run check:desktop`, `npm run check:composio`, intent and agent-speed tests, then `npm run ui`. Do not restart an existing bridge as part of these checks.

The [official WhatsApp business phone numbers documentation](https://developers.facebook.com/documentation/business-messaging/whatsapp/business-phone-numbers/phone-numbers) is the reference for a future business-number integration with webhook delivery. This is not an API for existing personal chats. This slice does not require moving or registering a personal number.

Unchanged badges and provider samples preserve their content-change time while latest successful observation time advances. Equal timestamps use stable identity ordering. Sample order does not change the displayed subject or content identity; email identity uses metadata rather than preview/body content. Dismissing either Gmail unread/possible-reply card dismisses both cards for that same account/sample. Changed evidence returns; an unchanged dismissed sample stays dismissed even after disappearance. Mirrored desktop/Web WhatsApp badges dedupe. Badge parsing accepts only bounded ASCII decimal counts 1–9999 in leading `(3) WhatsApp`, `[3] WhatsApp`, or `WhatsApp (3)` formats; signs, decimals, thousands separators, localized digits and unsupported layouts produce no badge inference.

## Exact adaptive timing and limits

- Local Windows title/session discovery: saved interval **B = 5–120 seconds** (default 15) remains the normal baseline. A changed observation starts three subsequent 5-second checks. Then three unchanged checks use B, and the fourth onward uses min(2B, 120 seconds). Source failure uses min(B × 2^n, 120 seconds), n starting at 1; recovery with changed evidence restores the burst. Quiet mode does not change these intervals. Explicit local refreshes can read local sources sooner; they cannot bypass the remote gate.
- Remote Composio: the first poll is immediate. Each selected provider/account keeps its own due time, change burst and fault streak. A changed sample (including removal or recovery) schedules two subsequent checks 15 seconds apart. If unchanged, the next two intervals are 60 seconds, then 120 seconds until something changes. A provider fault switches only that provider/account to **30, 60, 120, 240, 300 seconds**, capped at 300 until recovery. Healthy providers continue on their own cadence; a changing Outlook sample remains eligible every 15 seconds even while Gmail backs off to 300. A global account-discovery failure uses that same exponential sequence as a global gate. Not-due providers retain their cached cards and original observation/change timestamps, rather than being marked freshly observed. There are no push subscriptions or delivery guarantees.
- Local delays run after local collection finishes; each provider deadline runs from completion of its own attempt. Global discovery-error delays run from that failed discovery. Provider latency is additional, and the single remote cycle waits for its bounded provider work before another cycle starts; a slow provider can therefore add its remaining wait (up to 6 seconds), but does not impose its multi-minute retry delay on healthy sources. Desktop scheduling honors an earlier remote deadline, with a 5-second scheduling floor, so a long saved local interval does not postpone a remote retry. Cadence metadata exposes the local target interval/next scheduled check, remote cycle last-attempt/next-eligible time, and per-account last-attempt/next-eligible time and retry streak. The next remote cycle is the earliest provider due time subject to the global 15-second start floor (or the global discovery-error gate). Local scheduling is installed before broadcasting/returning its deadline; paused/disabled monitoring has no next deadline. Manual refresh and settings changes cannot start remote cycles less than 15 seconds apart. Pausing prevents further scheduled collection and invalidates pending UI results; already dispatched read-only SDK requests may finish.
- At most one remote cycle runs concurrently. Each cycle selects at most Gmail, Outlook and Calendar, executing at most one read tool per provider (10 mail items / 20 calendar results). Ownership checks currently require up to four account-list requests per cycle (one discovery plus one per tool); schema retrieval adds up to three metadata calls. At the fastest cadence this is at most four cycles/minute, up to 12 read-tool, 16 account-list and 12 schema calls/minute, excluding already in-flight latency. Gmail schema is cached; Outlook/Calendar validate current metadata each cycle. These are application-level SDK call bounds, not a steady-state target; SDK-internal HTTP retries are not configured or verified offline.
- Account discovery and each remote provider have 6-second UI wait bounds; local sources have 8-second bounds; optional AI briefing has a 20-second abort deadline and remains at most once/minute. Timed-out underlying reads retain source/account leases until settling, preventing overlapping retries even if an SDK ignores cancellation. A stuck SDK can therefore keep that provider unavailable until it settles or the caller restarts the bridge. Configuration epochs reject obsolete results, including after pause/resume and disconnect. Clocks and timers are injectable for deterministic offline tests.
- Global watch data older than 180 seconds is stale; a retained individual observation older than 330 seconds is labeled stale even if local discovery continues. UI observation times and cadence describe sampling, never actual mail arrival times. Workspace age tooltips distinguish last observation from evidence change. Active foreground work, voice, questions and approvals suppress watch interruptions; dismissed/obsolete evidence cannot create a new flash.

Offline coverage now includes the original email/WhatsApp regressions `scripts/test-workspace-cadence.mjs`, and real HTTP/WebSocket UI ingress tests in `scripts/test-monitor-ingress.mjs`, all run by `npm run check:workspace`. Live Composio key/tenant schemas and real Windows title behavior remain unverified. No authenticated WhatsApp content path is implemented.

Monitor snapshots carry a random per-process monitor `instanceId` and an increasing `revision`. Dismiss, configure, briefing and scheduling publications advance the revision even when collection `updatedAt` stays unchanged. All UI HTTP controls/GETs and event-stream updates share one acceptance path: only newer revisions of the current instance apply; an established instance can be replaced by a new event-stream instance, never by a delayed HTTP response. Previously observed instances are retired. HTTP requests captured before an instance switch and aborted responses (including abort during JSON decoding) cannot apply. Workspace renders accepted shared state directly, without a competing local HTTP snapshot copy. Obsolete WebSocket connections cannot deliver monitor messages or disconnect the current socket.
